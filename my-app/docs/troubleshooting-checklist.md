# Чек-лист диагностики

Используйте этот порядок как мини-лабораторную: симптом → гипотеза → команда → результат → восстановление.

## 1. Базовая проверка

- [ ] `docker compose ps` показывает backend в состоянии healthy, а frontend — running.
- [ ] `curl http://127.0.0.1:8080/api/healthz` возвращает `status=ok`.
- [ ] `curl http://127.0.0.1:8080/api/readiness` возвращает `status=ready`.
- [ ] `docker compose logs --tail=100 backend` не содержит traceback или restart loop.
- [ ] В dashboard связь с телеметрией — `онлайн`, а графики получают новые точки.

## 2. Нагрузка на CPU

- [ ] Запустите профиль CPU с 1 рабочим процессом и небольшой интенсивностью.
- [ ] Сравните CPU/load в dashboard и `docker stats`.
- [ ] Проверьте, растёт ли API latency одновременно с load average.
- [ ] Сформулируйте: это ограничение CPU, слишком много рабочих процессов или внешний соседний процесс?
- [ ] Остановите задание и убедитесь, что CPU/load снижаются.

## 3. Нагрузка на память

- [ ] Запустите профиль памяти на 64–128 МиБ.
- [ ] Сопоставьте memory percent с `free -h` и container limit.
- [ ] Проверьте, не появился ли OOM/restart: `docker inspect <container> --format '{{.State.OOMKilled}}'`.
- [ ] Остановите задание и убедитесь, что доступная память восстанавливается.

## 4. Дисковый ввод-вывод и заполнение диска

- [ ] Запустите профиль диска на 16–64 МиБ.
- [ ] Смотрите disk usage/write bytes и `df -h`.
- [ ] Проверьте, что временные файлы удаляются после завершения задания.
- [ ] Для более глубокого упражнения используйте `iostat`/`iotop`, если они установлены.

## 5. Задержка и ошибки HTTP

- [ ] Включите задержку API 500–1000 мс и сравните график задержки с `/api/healthz`.
- [ ] Включите долю ошибок 25–50% и посмотрите ошибки API.
- [ ] Проверьте коды ответов: `curl -i /api/metrics`.
- [ ] Отличите ошибку уровня приложения 503 от недоступности контейнера через healthcheck.

## 6. Деградация readiness

- [ ] Включите `Ухудшить readiness`.
- [ ] Убедитесь, что `/api/readiness` даёт 503, а `/api/healthz` остаётся 200.
- [ ] Объясните, почему оркестратор должен убрать сервис из трафика, но не перезапускать его как завершившийся процесс.
- [ ] Выключите переключатель и проверьте восстановление.

## 7. Восстановление и фиксация результатов

- [ ] Остановите все активные задания.
- [ ] Сбросьте задержку, error rate и деградацию readiness.
- [ ] Проверьте `docker compose ps`, логи и `/metrics`.
- [ ] Запишите первопричину, подтверждения, временное устранение и постоянное исправление.
- [ ] Если нужно полностью пересоздать стенд: `docker compose down && docker compose up --build -d`.
