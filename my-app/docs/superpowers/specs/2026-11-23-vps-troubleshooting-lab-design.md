# VPS Troubleshooting Lab — дизайн проекта

## Назначение

Учебное веб-приложение для развёртывания на VPS и безопасного воспроизведения типовых DevOps-инцидентов. Пользователь наблюдает состояние сервера, запускает контролируемую нагрузку, включает отказные режимы и расследует результат через графики, health-checks, журналы событий и Prometheus-совместимые метрики.

Целевая аудитория — начинающий DevOps-инженер, которому нужен практический стенд для отработки диагностики Linux, Docker и HTTP-сервисов.

## Цели

- Дать один понятный dashboard с realtime-метриками CPU, load average, RAM, disk usage, disk I/O, network I/O, процессами и состоянием API.
- Позволить запускать ограниченные профили CPU, памяти, диска, сети и HTTP-конкурентности.
- Дать учебные fault toggles: задержка API, процент ошибок, деградация readiness.
- Записывать историю действий пользователя и последние измерения в памяти процесса.
- Запускаться локально и на VPS одной командой через Docker Compose.
- Экспортировать `/metrics` в формате Prometheus, чтобы позже подключить Prometheus и Grafana без переделки API.
- Сделать сценарии нагрузки предсказуемыми: лимиты длительности, workers, объёма памяти и числа запросов.

## Не входит в первую версию

- Постоянное хранение метрик в базе данных.
- Аутентификация и multi-user режим.
- Автоматическое управление firewall, Docker, systemd или самим VPS.
- Реальные внешние DDoS/UDP flood-сценарии и неограниченная генерация нагрузки.
- Полноценная замена Netdata, node-exporter, Prometheus или Grafana.

## Антицели

- Нагрузка не должна запускаться бесконечно или принимать неограниченные значения от браузера.
- Приложение не должно выполнять shell-команды из пользовательского ввода.
- UI не должен скрывать, какой профиль нагрузки активен и когда он завершится.
- Сбой учебного приложения не должен приводить к удалению данных или изменению конфигурации VPS.

## Подходы

1. **Самодостаточный стенд (выбран).** React/Vite frontend, FastAPI backend, `psutil`, Docker Compose, realtime polling, ограниченные генераторы нагрузки и `/metrics`. Минимум компонентов, понятный код, быстрый запуск на VPS.
2. **Prometheus + Grafana + генератор нагрузки.** Production-подобнее и лучше для изучения observability, но добавляет несколько сервисов и конфигураций. Подключается следующим этапом к уже готовому `/metrics`.
3. **Микросервисный стенд.** Отдельные API, worker, Redis и reverse proxy дают больше сетевых сценариев, но увеличивают сложность раньше времени. Может стать второй лабораторной итерацией.

Выбран подход 1: сначала пользователь должен научиться видеть симптом, формулировать гипотезу и проверять её на одном сервисе. Контракт метрик и Docker-структура оставляются расширяемыми для перехода к подходу 2.

## Архитектура

### Backend

- Python 3.12, FastAPI, Uvicorn, Pydantic Settings, `psutil`.
- Фоновый sampler снимает snapshot примерно раз в секунду и хранит кольцевой буфер последних 10 минут.
- `GET /api/metrics` возвращает текущий snapshot и последние точки для графиков.
- `GET /metrics` отдаёт основные gauges/counters в Prometheus text format без обязательной зависимости от Prometheus.
- `GET /api/healthz` всегда отвечает liveness; `GET /api/readiness` отражает включённую деградацию и fault-состояние.
- `POST /api/load/jobs` запускает профиль нагрузки, `GET /api/load/jobs` показывает активные jobs, `DELETE /api/load/jobs/{id}` останавливает job.
- `GET/PATCH /api/faults` читает и изменяет контролируемые fault toggles.
- Ресурсные лимиты: CPU workers не больше числа CPU и 8, память не больше 512 MiB на job, диск не больше 256 MiB, HTTP concurrency не больше 50, длительность не больше 300 секунд.
- Aggregate safety limits: не больше 2 активных jobs и не больше 384 MiB суммарно зарезервированной job-памяти; оставшийся бюджет контейнера предназначен backend/sampler.

### Frontend

- React 18 + TypeScript + Vite.
- Recharts для line/area charts и обычный CSS без тяжёлой UI-системы.
- Dashboard: верхние карточки состояния, сетка графиков, active load jobs, fault controls, event timeline и учебные подсказки.
- Данные опрашиваются каждые 2 секунды; при ошибке API показывается stale/offline состояние, графики не маскируют потерю данных.
- Все параметры нагрузки проходят клиентскую валидацию, но backend остаётся источником истины и повторяет ограничения.

### Развёртывание

- `docker-compose.yml` запускает `backend` и `frontend`.
- Nginx в frontend-контейнере раздаёт собранный React и проксирует `/api` и `/metrics` на backend.
- Для базового режима метрики относятся к контейнеру приложения. В документации будет отдельный Linux/VPS режим с пояснением про `pid: host`, права и риски.
- Compose по умолчанию публикует frontend только на `127.0.0.1`; внешний bind через `FRONTEND_BIND=0.0.0.0` является явным решением оператора и требует firewall/VPN.
- `.env.example` содержит только безопасные настройки: адрес backend, интервалы sampler и лимиты нагрузки.

## Учебные сценарии

- CPU saturation: постепенно поднять CPU, увидеть рост load average и latency.
- Memory pressure: занять ограниченный объём RAM, увидеть доступную память и поведение readiness.
- Disk pressure/I/O: генерировать временные записи, наблюдать disk usage и write bytes.
- Network/HTTP concurrency: создать много внутренних запросов и связать concurrency с latency/error rate.
- Slow API: включить задержку, найти её по latency и readiness.
- Error storm: включить процент 5xx, отличить application errors от инфраструктурной проблемы.
- Recovery: остановить jobs, выключить faults и проверить, что графики и health-check возвращаются к норме.

## Проверка качества

- Backend unit/API tests на валидацию лимитов, lifecycle job, sampler snapshots, faults и health endpoints.
- Frontend tests на отображение offline/stale состояния, отправку ограниченных параметров и обновление графиков.
- Smoke-check: `docker compose config`, backend test suite, frontend build.
- Документация должна содержать запуск, остановку, безопасные пределы нагрузки, примеры `curl`, troubleshooting checklist и идеи для расширения Prometheus/Grafana.

## Решения, оставленные builder'у

- Точное разбиение модулей и имена внутренних классов — по принципу одной ответственности.
- Визуальный стиль — тёмная dashboard-панель с контрастными статусами, чтобы было удобно работать на VPS через браузер.
- Внутренний транспорт realtime — polling в первой версии; WebSocket не нужен, пока частота данных 1–2 секунды.
